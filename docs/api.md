# API

一個 heap 一個 mutator，GC 只在安全點（兩個操作之間）開始和收尾，所以那時沒有沒 root 的指標，也不掃 stack。`unsafe` 只在 `elise` 裡；用它的程式碼不寫 `unsafe`，論證在 [`soundness.md`](soundness.md)。`#[derive(GcObject)]` 在 `elise-derive`。heap 怎麼運作見 [`design.md`](design.md)。

## 型別一覽

| 型別 | 對應 cppgc | 用途 |
| --- | --- | --- |
| `Heap` | `cppgc::Heap`（young generation 是 V8 的 `Heap` 的 scavenger） | 一個 heap：`HeapOptions::driven` 的由 JS engine 推進 old 的 marking（`start_marking`、`advance_marking`、`finish_marking`，下面的「和 JS engine 一起標記」），`used_bytes` 是 engine 要知道的大小；`mutate` 跑一個操作（開始前是安全點），`read` 跑一個不配置的操作（不經過安全點，借共享的 `&Heap`：這種操作可以一個在另一個裡面，不會和 GC 重疊），`collect` 在安全點做 full GC（正在 concurrent marking 的話先收掉它；driven 的 heap 不行：它的 full GC 是 engine 的），`scavenge` 只收 nursery，`is_marking` 是不是正在 concurrent marking，`is_sweeping` 是不是上一次 full GC 的 sweep 還在背景跑，`stats`（含上一次 full GC 的 `GcRecord`：停頓和 mark、sweep、finalize 各自的時間，標到的物件和 bytes，worker 掃了幾個，是不是 concurrent 的、它開始的停頓、收尾的停頓裡標了幾個、engine 推進的步驟裡 heap 的 thread 標了幾個；concurrent marking 做完的次數、其中撞到門檻收尾的次數、worker 在背景標的時間合計；worker 在背景 sweep 的時間、heap 的 thread 在停頓外 sweep 的時間和頁數；上一次 scavenge 的 `ScavengeRecord`：時間，留在 nursery 和升到 old 的物件和 bytes，跑了幾個 finalizer）、`roots`。`HeapOptions::nursery_bytes` 是 nursery 一開始的大小（預設 1 MiB，0 是沒有 nursery），`max_nursery_bytes` 是它最多長到多大（預設 16 MiB），`HeapStats::nursery_bytes` 是現在的大小 |
| `Mutation<'gc>` | `AllocationHandle` | 一個操作：`alloc` 配置物件，`alloc_in` 從一個 site 配置，`alloc_beside` 配在擁有者的那一代（擁有者在 old 就直接放 old：掛在它身上、和它活得一樣久的資料，例如節點的文字和屬性），讀寫邊都要它；`new_id` 給物件一個 id、`by_id::<T>` 用 id 找它（id 表）；`pretenured` 裡的配置直接放 old（V8 的 `AllocationType::kOld`），給呼叫的人知道會活很久的物件（例如 parser 建的初始文件） |
| `Site`、`SiteStats`、`PretenureDecision` | V8 的 `AllocationSite` | 一個配置的地方，在那裡宣告（`static SITE: Site = Site::new();`，`cx.alloc_in(&SITE, ..)`），或執行時建了 leak 掉（不是程式裡的地方的，例如重播的錄到的型別）；每個 heap 各自數、各自決定要不要把它的物件直接放 old，`Heap::site` 看它的計數和決定。一個 process 最多 65535 個 |
| `Gc<'gc, T>` | `T*` | 操作裡的物件：raw pointer，帶著操作的 invariant lifetime，不能帶出操作 |
| `Member<T>` | `Member<T>` | 物件裡的邊：cage 裡的 32 位元 offset，0 是 null。`[Member<T>; N]` 也可以當欄位：N 條連續的邊 |
| `Erased` | `Member<GarbageCollectedMixin>` 這類指向多種型別的邊 | 任何型別的物件：`Member<Erased>` 的邊可以指向不同型別的物件，`Gc::erase` 把 `Gc<T>` 換成它；沒有欄位。`Gc::<Erased>::downcast::<T>` 照物件 header 的型別轉回去，不是 `T` 是 `None`（DOM 的節點的「種類的資料」一格指向幾種型別） |
| `Persistent<T>` | `Persistent<T>` | root：heap 的 root 表的一格，可以留過操作 |
| `WeakMember<T>` | `WeakMember<T>` | weak 的邊：不留住它指的物件，物件死了之後 GC 把它清成 0（old 的物件由 full GC，young 的由 scavenge）。`get(cx)` 回 `Option<Gc>`，`set`；`[WeakMember<T>; N]` 也可以當欄位 |
| `Id` | Blink 的 `DOMNodeId` | heap 的 id 表裡的編號：`new_id` 給，一直往上數、不重複；物件活著時 `by_id` 找得到，死了之後永遠找不到（`from_raw` 從寫下的數字讀回來，任何數字都安全）。`HeapStats::id_chunks` 是表現在的塊數 |
| `EphemeronPair<K, V>` | `EphemeronPair<K, V>` | ephemeron：一條 weak 的 key 和一條 value，value 只在 key 活著時活著（value 指回 key 不會留住 key）。`key(cx)`、`value(cx)`（key 死了兩個都是 `None`）、`set(cx, key, value)`；`[EphemeronPair<K, V>; N]` 也可以當欄位。會長大的容器（像 Oilpan 的 weak key 的 `HeapHashMap`）之後照需要建在它上面 |
| `Mutation::engine_address`、`from_engine` | cppgc 的物件的位址（`Object::Wrap`、`Unwrap`） | JS engine 的 wrapper 存的物件的位址：driven 的 heap 裡帶 `JsEdge` 的型別一律在 old、不搬，所以位址一直有效；`from_engine` 讀回（`unsafe`：呼叫的一方保證那是這個 heap 的活的 `T`；不在這個 heap 的 cage 裡就 panic；marking 期間經過讀取的 barrier） |
| `WrapperMarker`、`WrapperLocal` | cppgc 的 `CppMarkingState`（給 V8 的 marking thread 用） | engine 的 marking thread 把標到的 wrapper 的物件交過來：`start_marking` 給 `WrapperMarker`，每個 thread 一個 `local`，`hand`（`unsafe`：那個位址是這個 heap 的活的物件；不在 cage 裡的不理）、`publish`（drop 時也是） |
| `JsEdge` | `TracedReference`（cppgc 的物件裡的） | 物件指向 JS engine 的物件（節點的 wrapper）：engine 自己的參照（V8 的 `TracedReference`，8 bytes、對齊 8），在物件裡，heap 建成空的之後從不讀寫，`as_ptr` 給 engine 寫；engine 推進的 marking 掃到物件時把它的位址交給 engine。物件死了什麼都不用做（engine 已經放掉沒標到的）。`type_index::<T>()` 是型別在表裡的編號（engine 給每個型別一個 tag），一定小於 `MAX_TYPES`（4096），`js_edges_of` 從物件的位址找出它的 JS 的邊（engine 丟掉 wrapper 時找回那一格）。沒有 engine 驅動的 heap 裡，這 8 bytes 沒人讀寫（沒有 engine，marker 不交出 JS 的邊），是 embedder 的一個 word：`embedder_word`、`set_embedder_word`（一開始是 0，跟著物件搬；在 driven 的 heap 裡 panic），wasm 文件的節點放它的 main Store 的 handle |
| `JsEdgeSink`、`JsEdgeLocal` | V8 的 `UnifiedHeapMarkingState`（給 cppgc 的 marker 用） | engine 收 JS 的邊的地方：marker 的每個 thread 一個 local |
| `WeakPersistent<T>` | `WeakPersistent<T>` | weak 的 root：heap 的另一張 root 表（weak 的）的一格，可以留過操作；`get(cx)` 回 `Option<Gc>`，物件死了是 `None` |
| `External<T>`、`LocalExternal<T>` | （無：cppgc 的物件可以直接帶原生資料） | 物件裡的原生資料（`Box`、`Vec`、`Arc`……）：GC 不讀它，它的 `Drop` 是物件唯一的 finalizer。`External` 要 `T: Send`，finalizer 在 sweep 的 worker 上跑（V8 在 worker 上放 ArrayBuffer 的記憶體）；不是 `Send` 的（`Rc`、`Persistent`）放 `LocalExternal`，物件的 finalizer 在 heap 的 thread 上跑（cppgc 的都是） |
| `LocalToken`、`TokenCell<T>` | （無：Blink 直接讀寫，靠 `DocumentLifecycle` 的 DCHECK） | 用 token 靜態地分開讀和寫的 cell（qcell 的 `TLCellOwner`、`TLCell`）：一個 thread 同時只有一個 `LocalToken`（`new` 時檢查），`get(&token)` 給借用的參照，`get_mut(&mut token)`、`replace` 寫；token 不離開它的 thread，cell 不是 `Sync`。沒有計數、沒有借用的旗標。DOM 的 style 的結果放在它裡面（在 `External` 裡）：style 那一段借 token 的 `&mut` 寫，layout 借 `&` 讀 |
| `Heap::walk`、`Walk`、`HeapObject`、`Edge`、`EdgeKind` | V8 的 snapshot generator 的 `HeapObjectIterator`、cppgc 的 `HeapVisitor`（它的 graph builder） | heap snapshot 用：在安全點上先收完上一次 full GC 的 sweep（V8 拍 snapshot 之前也收完自己的），跑一個操作，交出 heap 拿著的每個物件（`Walk::objects`：上一次 GC 留下的和之後配置的，垃圾也算；full GC 之後就是活的）和 root 拿著的（`roots`）。每個物件有型別的名字和編號（`type_name`、`type_index`）、大小（header 加欄位，`size`）、位址（`address`，engine 的 wrapper 存的就是它）、照欄位名字的邊（`edges`：`Member` 的是 strong、`WeakMember` 的是 weak、ephemeron 的 key 是 weak、value 帶著 key（key 活著它才活），陣列的沒有名字；執行時的型別的物件照它的 layout，沒有名字、`I31` 不算）和 JS 的邊（`js_edges`），`get` 拿回 `Gc<Erased>`。marking 期間交出的物件照 weak 的讀取標上（交出的可能是 marking 會放掉的）。走遍每一頁，只給 snapshot |
| `HeapVector<T>` | `HeapVector<Member<T>>` | 會長大的邊的清單，本身是 heap 的物件；`clear` 清空、留著容量（一再重填的清單只配置一次），清掉的邊不留住東西 |
| `raw::TypeRange`、`raw::Layout`、`raw::ArrayLayout` | cppgc 的 `GCInfoTable`（執行時登記的部分沒有對應：cppgc 的型別都是 C++ 的） | embedder 執行時登記的型別（wasm engine 的 GC 型別）：`TypeRange::reserve(len)` 保留一段連續的編號（每個 engine 一段，都在 `MAX_TYPES` 以上、`raw::MAX_INDEX` 以下），`register(id, &layout, keepalive)` 在 `base + id` 登記一個型別，回傳它的編號；layout 是大小、邊的 offset（遞增、4-aligned），array 另外有長度的位置和元素的大小（元素可以是邊）。layout 不對、id 超出、那一格還有型別時回 `RegisterError`。`retire(id)`（`unsafe`：之後不再配置它、也沒有它的物件到得了）之後，那一格等每個當時活著的 heap 都做完一次之後才開始的 full GC 才放掉（連同 keepalive，在做完的那個 thread 上 drop），之後才能再登記。`TypeRange` drop 時空的格子還回去，退休的等放掉之後才還，還登記著的不還 |
| `raw::alloc`、`raw::alloc_array` | — | 照編號配置、清成 0（每條邊是 null），回 `Gc<'gc, Erased>`：`Persistent<Erased>` 留住它、`Member<Erased>` 指向它，`downcast` 到任何 Rust 型別都是 `None`。`alloc_array` 寫好長度，太大時回 `None`；編號不是執行時的型別、已經退休、struct 和 array 用錯時 panic。`raw::data` 是物件的 bytes 的指標（embedder 寫資料用，邊和長度不經過它），`raw::index_of` 是物件的型別的編號，`raw::write_edge`、`read_edge`（`unsafe`：`at` 是型別的邊）讀寫一條邊：none、物件或 `I31`（`Option<raw::Ref>`），寫時經過和 `Member::set` 一樣的 barrier |
| `raw::Ref`、`raw::I31`、`raw::bits`、`raw::read_bits`、`raw::write_bits` | V8 的 `Smi`（tagged 的格子用最低位元分辨整數和物件）、wasmtime 的 `I31` 和 `VMGcRef` | 執行時的型別的邊放的是 none、物件（`Ref::Object`）或 31 位元的整數（`Ref::I31`，wasm 的 `i31ref`）：GC 跳過整數。`I31` 照 wasmtime 的：`wrapping_u32`、`wrapping_i32`、`new_u32`、`new_i32`（放不下時 `None`）、`get_u32`、`get_i32`（零擴展和符號擴展）。邊的 bits 是 wasm engine 的碼裡的形式：0、物件在 cage 裡的 offset、整數左移一位再設最低位元；`bits` 從值算出來，`read_bits`、`write_bits`（`unsafe`：`at` 是型別的邊；寫的 bits 是 0、整數的，或這次操作裡拿到的同一個 heap 的活物件的 offset）直接讀寫，寫時經過和 `write_edge` 一樣的 barrier |
| `Heap::enter_frames`、`leave_frames`、`in_frames`、`safepoint_with_roots`、`scavenge_with_roots`、`collect_with_roots` | cppgc 的 `EmbedderStackState`（stack 上有沒有 heap 的指標）；wasmtime 的 `GcHeap::gc` 和 `GcRootsIter` | wasm engine 的 frame 在 stack 上、拿著物件的 bits（wasm 呼叫 embedder 時）：進出各呼叫一次，可以巢狀；`leave_frames` 是 `unsafe` 的（離開的 frame 不再拿著 bits：少算了，安全點就會搬動、放掉它們拿著的），在 frame 裡 drop 的 heap 整個 leak（cage、頁和物件都留著，engine 的碼可能還在讀寫）。在裡面時 `mutate` 的安全點不開始要讀 root 的 GC（scavenge、full GC、concurrent marking 的開始和收尾；nursery 滿了改配置到 old），sweep 和 marking 照跑；`collect`、`scavenge` panic。engine 在拿得到全部 root 的地方（配置失敗時、`Store::gc`）呼叫 `*_with_roots`（`unsafe`：每個 root 是 0、`I31` 的 bits 或這個 heap 的活物件的 offset；同樣的 root 照同樣的順序交兩次）：`roots` 對每個 root 呼叫給它的函式，GC 跳過 0 和 `I31`、把物件當 root，搬動之後寫回新的 bits；第二次交出的數目不同時 panic。`safepoint_with_roots` 做 frame 外的安全點這時會做的，`scavenge_with_roots`、`collect_with_roots` 照名字。在裡面時 `should_collect` 說的是 `safepoint_with_roots` 會不會做事 |
| `Heap::set_roots_source`、`has_roots_source`、`RootsSource` | Blink 的 heap 經過 V8 的 `EmbedderRootsHandler` 問 V8 拿著它的哪些物件；wasmtime 的 `Store::trace_roots`（它的 global、table、host 的 root、暫停的 fiber 的 stack） | embedder 在 heap 的表之外、兩次 GC 之間也拿著的 root（wasm engine 的 store 的）：`set_roots_source(Some(..))` 給 heap 一個來源，`None` 拿掉（`unsafe`：被換掉的來源的 root 不再有人需要），`has_roots_source` 問有沒有（一個 embedder 不蓋掉另一個的）。來源在 GC 期間留在原位（GC 不問它），它 panic 時也還在。每個讀 root 的 GC 都問它：`mutate` 的安全點的、`collect`、`scavenge` 的，和交出 frame 的 root 的（`*_with_roots`，接在 frame 的之後）；GC 之後照同樣的順序再問一次、寫回搬動後的 bits。`RootsSource` 是 `unsafe` 的 trait（契約同 `*_with_roots`：每個 root 是 0、`I31` 的 bits 或這個 heap 的活物件的 offset；同樣的 root 照同樣的順序交兩次）。`roots` 給不了時（拿著 root 的一方正在用，例如它的 frame 在 stack 上）回 false、一個都不給：那時不做讀 root 的 GC，和在 frame 裡一樣（安全點不做、`collect`、`scavenge` 什麼都不做、交出 root 的 GC 不做，之後的 bits 的配置不再等）。第一次給了、第二次給不了，或給的數目不同時 panic |
| `raw::alloc_bits`、`raw::alloc_array_bits`、`raw::AllocError`、`raw::read_bits_in`、`raw::write_bits_in`、`raw::from_bits` | wasmtime 的 `GcHeap::alloc_raw`（它的兩種失敗）、`write_gc_ref`；V8 的 wasm 的 `struct.new` 由 JIT 的碼或 runtime 直接配置，不經過 Blink | 給 engine 的碼、不經過操作的配置和讀寫邊：在 `&mut Heap` 上（讀的在 `&Heap` 上），操作裡呼叫不到，也不付操作的固定成本。`alloc_bits`、`alloc_array_bits` 回物件的 bits，從不 GC：GC 該做時回 `AllocError::GcDue`，engine 收齊 root、呼叫 `safepoint_with_roots` 之後重試，緊接著的那一次配置不再等（wasmtime 在 GC 之後只重試一次）；array 太大是 `TooLarge`（先檢查）。`read_bits_in`、`write_bits_in`（`unsafe`：物件是這個 heap 的活物件的 bits，`at` 是型別的邊，寫的 bits 同 `write_bits`）照 bits 讀寫一條邊，寫時經過和 `write_bits` 一樣的 barrier。`from_bits`（`unsafe`：bits 是 0、`I31` 的，或 frame 拿著的活物件的）在操作裡把 bits 變回 `Ref`（wasm 傳給 host function 的參數） |
| `raw::cage_in`、`raw::size_at`、`raw::barrier_state_in`、`raw::new_id_in`、`raw::id_lives_in`、`raw::satb_in`、`raw::remember_in`、`raw::HeapAlive`、`raw::alive_in` | V8 的 wasm 物件在 V8 自己的 heap 裡，沒有對應 | `EngineHeap` 的那幾個方法用在任何 `Heap` 上（engine 借 embedder 的 heap 時：wasmtime 的 store 借 machopo 的 DOM 的）：`cage_in` 是 cage 的開頭，heap 活著時不變；`size_at`（`unsafe`：cage 是一個 heap 的、bits 是它的活物件）只從物件讀它的大小，不用借 heap（engine 記下 cage 的開頭，讀物件不經過 heap）；`barrier_state_in`、`satb_in`、`remember_in` 是 barrier，`new_id_in`、`id_lives_in` 是 id，同 `EngineHeap` 的。`alive_in` 給 `HeapAlive`：heap drop（或在 frame 裡 drop、leak）時清掉，記下 cage 的 engine 讀之前先在 heap 的 thread 上問它；`is` 是某個 `Heap` 是不是它說的那個（別的 heap 永遠不是，即使 map 在同一個位址：拿著它的一方留著它的分配） |
| `raw::EngineHeap`、`raw::CAGE_BYTES` | wasmtime 的 `GcHeap`（`Send + Sync`，跟著 `Store` 換 thread）；V8 的 isolate 在 `Locker` 底下：可以在任何 thread 上，一次一個 | 只有 engine 的碼經過 bits 用的 heap：不跑操作（沒有 `mutate`），所以沒有 `Persistent`、`LocalExternal` 這些留在 thread 上的東西，它是 `Send` 和 `Sync`，跟著擁有它的一方換 thread。`new` 給 platform（沒有 worker 時用 `InlinePlatform`）。`alloc`、`alloc_array`、`read_bits`、`write_bits` 是上面的 `alloc_bits` 等，`cage`、`size`、`barrier_state`、`new_id`、`id_lives`、`satb`、`remember` 是 `cage_in` 等，frame 和交出 root 的 GC 同 `Heap` 的（`leave_frames` 是 safe 的：它不跑操作，沒有不交 root 的安全點，frame 只影響 `should_collect`）。`cage()` 是 cage 的開頭，物件的資料在它之後 bits 的位置，`CAGE_BYTES` 是 cage 的大小（每個物件的 bits 都比它小）；`size`（`unsafe`：活物件的 bits）是物件照 layout 的位元組數（array 包括元素），`used_bytes` 同 `HeapStats::used_bytes`。`new_id`（`unsafe`：活物件的 bits）給物件一個 id（同 `Mutation::new_id`），`id_lives` 是它的物件還活著沒有：不標物件、不給物件，給 engine 知道哪些死了、放掉它在 heap 外的資料（wasmtime 的 `externref` 的 host data）。`&self` 的方法只讀 cage 的開頭、frame 的計數、用量的計數和物件的位元組，其他的要 `&mut self` |

## 基本用法

```rust
use std::cell::Cell;

use elise::{GcObject, Heap, HeapOptions, Member, Persistent};

#[derive(GcObject)]
struct Node {
    parent: Member<Node>,
    id: Cell<u32>,
}

let mut heap = Heap::new(HeapOptions::default());
let root = heap.mutate(|cx| {
    let parent = cx.alloc(NodeInit { parent: None, id: Cell::new(1) });
    let child = cx.alloc(NodeInit { parent: Some(parent), id: Cell::new(2) });
    assert_eq!(child.parent.get(cx).unwrap().id.get(), 1);
    Persistent::new(cx, child)
});
heap.collect();
heap.mutate(|cx| assert_eq!(root.get(cx).parent.get(cx).unwrap().id.get(), 1));
```

## 規則

- **物件是 `#[derive(GcObject)]` 的 struct**，欄位有名字、沒有泛型參數，每個欄位是 `Member`、`[Member<T>; N]`、`WeakMember`、`[WeakMember<T>; N]`、`EphemeronPair`、`[EphemeronPair<K, V>; N]`、`HeapData`、`External` 或 `LocalExternal`；放 `Box`、`Vec`、參照的編不過（放進 `External` 的不是 `Send` 也編不過，錯誤指向 `LocalExternal`），指到那個欄位。derive 產生 `{名字}Init<'gc>`：欄位一樣，`Member<T>` 換成 `Option<Gc<'gc, T>>`（`[Member<T>; N]` 換成 `[Option<Gc<'gc, T>>; N]`）；一個 crate 裡要很多個大小不同的類別時（machopo 的 `gc_bench` 的重播），每個放在自己的 `const _: () = { .. };` 裡，經過 trait 的 impl 拿得到，不用一個一個取名字；`cx.alloc(Init { .. })` 直接寫進 heap，所以 `Member` 不會出現在 heap 外。欄位叫什麼都可以（產生的 `__init` 的參數名稱是欄位不會用的 `__gc_init`、`__gc_slot`）。
- **物件不能實作 `Drop`**（編不過）：finalizer 只有 `External` 和 `LocalExternal` 的值的 `Drop`。兩者都要 `T: 'static`，裝不進 `Gc`，所以 finalizer 碰不到 heap（`Persistent` 是 `'static`，可以裝進 `LocalExternal`，那會讓它指的物件一直活著；它不是 `Send`，裝不進 `External`）。derive 在編譯時從欄位算出型別的 finalizer 在哪裡跑：有 `LocalExternal` 的 drop glue 是 heap 的 thread，只有 `External` 的是 sweep 的 worker（`HeapField::MAIN_THREAD_DROP`、`TypeInfo` 的 `Finalizer`）。
- **物件只借出 `&T`**：會變的欄位用 `Cell`、`RefCell`；邊用 `Member::get`、`set`。
- **`Gc` 不能留過操作**：要留下來的用 `Persistent`。一個操作裡不會 GC，所以 `Gc` 是 raw pointer，不用 root。
- **兩個 heap 的東西不能混用**：`Gc` 的 lifetime 擋掉大部分；讀 `Member`、`Persistent` 時另外檢查是不是這個 heap 的，不是的話 panic。
- 物件最大是 cage 的四分之一（1 GiB）。cage 滿了（4 GiB）時 panic：操作裡不會 GC。每個 large object 至少佔 256 KiB 的位址空間（實體記憶體只 commit 用到的），所以 cage 最多放約一萬多個。
