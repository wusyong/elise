# 怎麼運作

heap 的各個部分，和每一處對照 V8、cppgc 的做法、為什麼不一樣。API 見 [`api.md`](api.md)，safe code 不會造成 UB 的論證見 [`soundness.md`](soundness.md)。

- **Cage**：每個 heap 保留 4 GiB、對齊 4 GiB 的位址空間（沒有權限），用到時才 commit（macOS、Linux 用 `mmap` / `mprotect`，Windows 用 `VirtualAlloc`）。邊是 cage 裡的 offset，解壓是 cage 的起點加上 offset。第 0 頁不用，所以 offset 0 是 null。Miri 底下沒辦法保留位址空間，cage 是 16 MiB、一開始就配置好的記憶體，discard 什麼都不做。
- **頁和 size class**：256 KiB 一頁，每頁只放一種 size class 的格子：到 128 bytes 每 16 bytes 一級，之後每級約大 12.5%（mimalloc 的間距），到 32 KiB，共 52 級（頁尾的浪費最多 8.6%）。每格是 8 bytes 的 header 加上物件；格子 16 bytes 對齊，物件 8 bytes 對齊。大小混放（V8、cppgc）要讀每個物件的 header 才找得到下一個，照大小分的頁從位址算得出第幾格。
- **Large object**：大於 32 KiB 的物件（含 header）獨佔一段連續的頁，header 在第一頁的開頭；只 commit 它用到的 bytes（照作業系統的頁大小進位）。
- **Young generation**（V8 的 scavenger）：新的物件 bump 到 nursery 的頁上，大小混放、一個接一個（8 bytes 對齊），nursery 的頁數到了它現在的大小時，這個操作剩下的配置改放 old（不在操作中途 GC），下一個安全點做 scavenge。大於一格的物件、`pretenured` 裡的和決定 tenure 的 site 的一開始就在 old。nursery 的大小照 V8 的 `ResizeNewSpace`：scavenge 累積活下來的 bytes 超過它的大小時加倍，最多 `max_nursery_bytes`；full GC 時，上次 full GC 之後的 scavenge 留下的不到看過的 1/16 就減半，不小於一開始的大小，累積重新算起。哪些頁是 young 記在一張每頁一個 byte 的表上（V8 的 page flag），只在安全點改。
- **Write barrier 和 slot set**：寫 `Member`（`set`、配置時的 init、`HeapVector` 的寫入和它自己的 `store`）時，值在 young 的頁上而被寫的格子不在時，記進那一頁（或 large object）的 slot set：每 4 bytes 一個 bit，第一次記時才配置（V8 的 `OLD_TO_NEW`）。slot set 在 heap 上一張每頁一格的表裡，bitmap 用 CAS 換上、bit 用 atomic 的 or 設，scavenge 的 thread 可以一起記。判斷是讀兩次 young 的表。邊是 std 的 `AtomicU32`（`Member` 是 `repr(transparent)` 的它，`HeapVector` 的格子用 `from_ptr`）：concurrent marking 的 worker 在 mutator 寫的同時讀；marking 沒在進行時 relaxed 寫，進行中先過 SATB 的 barrier（下面的「Concurrent marking」）再 release 寫。
- **Scavenge**（`crates/elise/src/heap/young.rs`）：在安全點，交給 heap 的 platform（像 marking），從 root 表和 slot set 記著的邊出發，把 from-space（nursery 現在的頁）裡活的物件 copy 出去，copy 推進分段的 worklist、誰拿到誰掃；slot set 照頁切成工作，湊滿一段才給 worker，root 表在呼叫的 thread 上。第一次活下來的留在 nursery（新的頁，header 標 `AGED`），第二次的升到 old（V8 的 semi-space 的 age mark）。每個 thread 複製到自己的 to-space LAB（一次 32 KiB）和自己的每一級的區段，拿的時候才拿 heap 的鎖。兩個 thread 搶同一個物件時各自複製，再用一次 64 位元的 CAS 在舊的 header 寫上去向（`FORWARDED`，V8 的 map word）：輸的用贏家的，自己那份在最上面就退回、不然留著。LAB 的尾巴填空段（或退回），worker 的區段還回頁上。還指向 young 的老邊放回 slot set。死的物件不讀，只有 nursery 的 finalizer 清單上沒被搬走的，跑它的 finalizer。from-space 的頁進 pool（debug build 先填毒值）。整頁升上去（V8 的 page promotion）還沒做。
- **照 site pretenure**（V8 的 `PretenuringHandler`，`crates/elise/src/site.rs`）：從 site 配置的物件，header 的 flags 的高 16 bit 是 site 的編號（V8 是在年輕的物件後面放 `AllocationMemento`），copy 和升級都留著。每個 heap 數每個 site 在 nursery 配置的、和其中第一次 scavenge 就活下來的（平行的 scavenge 每個 thread 各數、結束後合起來），每次 scavenge 之後：配置滿 100 個、活下來 80% 以上的 site，nursery 至少 8 MiB（或它最大的）時 tenure，之後的配置直接放 old，不然記成「可能」等 nursery 長大；不到 80% 的不再判斷；計數歸零（V8 的門檻）。full GC 標記時數每個 site 被標到的物件（每個 thread 記目前的 site 和連續的數目，換了 site 才寫回：連續的物件大多同一個 site，每個都寫回陣列時小物件的鏈標記慢六分之一），tenure 的 site 被標到的不到它在 old 的物件（上次標到的加上之後進 old 的）的 10% 時撤回、回到 nursery 重新量（V8 看的是整個 old 的存活率，全部一起撤回：它的 memento 不跟著升上去）。`HeapStats::pretenured_objects` 是因為 site 而直接放 old 的配置。
- **Header**：型別在 process 的型別表裡的編號（4 bytes）和 flags（4 bytes：nursery 裡活過一次的 `AGED`；scavenge 時被 copy 走的 `FORWARDED`，這時第一個 word 是新的位置；高 16 bit 是 site 的編號）。型別表照 cppgc 的 `GCInfoTable`：每個型別的 layout（大小、`Member` 的 offset、drop glue）在 derive 產生的 static 裡，第一次配置時拿到編號，同時算好一份邊的 offset 清單（`[Member<T>; N]` 展開成 N 個），mark 照這份清單讀邊，不一個欄位一個欄位走 layout（graph 型的圖每秒多標約 15%）。static 的型別最多 4096 個（`MAX_TYPES`）；表有 2^18 格（2 MiB 的零，沒用到的頁不佔實體記憶體；cppgc 是 2^14），上面的給 embedder 執行時登記的型別（`raw`，wasm engine 的 GC 型別）：embedder 為每個 engine 保留一段編號，用自己的 id 在那段裡登記 layout（大小、邊的 offset，array 的長度和元素），elise 檢查過 layout、算好同樣的邊的清單，mark 和 scavenge 查同一張表、讀一次。它們的邊也可能放著 31 位元的整數（wasm 的 `i31ref`，照 wasmtime：整數左移一位、最低位元設成 1；V8 的 Smi 也是用最低位元分辨）：marker、scavenge 和 verifier 讀到時跳過，寫的 barrier 不收；scavenge 經過 slot set 的值都檢查（記下的格子之後可能被寫成整數），Rust 的型別的邊和 mutator 的路不變。不再用的型別退休之後，等每個當時活著的 heap 都做完一次之後才開始的 full GC 才放掉、那一格才給別的型別：在那之前，進行中的 marking 的快照和經過死掉的 old 物件的 slot set 的 scavenge 還可能讀到它的死物件的 header；那次 full GC 開始時清空 nursery、它的 sweep 釋放所有的這種物件。計數和退休的清單在一個全域的鎖底下，只在 heap 的建立和 drop、full GC 的開始和 sweep 做完時碰，配置和標記的路不變。
- **Bitmap**：每頁旁邊（heap 外）兩張 bitmap，一格一個 bit。`marks` 是活的物件：GC 開始時清掉、marking 設上活的。配置不看它（看 sweep 找出的空區段），所以新的物件只在 debug build 設上，讓下一次 GC 知道它死了要填毒值（concurrent marking 進行中另外整段標黑，下面）。`marks`（`page::Marks`：頁的起點、格子的大小和倒數、atomic 的 bit）在頁自己的配置裡（`OwnedMarks`，不用 `Box`：`Box` 跟著頁搬動時，Stacked Borrows 下 `MarkTable` 的指標就失效）、不會搬，heap 上一張每頁一格的表（`MarkTable`，16384 格的 atomic 指標，像 slot set 的表）指向它，頁變成某一級或 large object 時寫進去、釋放前拿掉（都在安全點）：marker 經過它找 mark bit，不碰會在 mutator 拿新頁時變長的頁的狀態。`finalizable` 是有 drop glue 的物件，寫完時設上。從 offset 算第幾格用每一級預先算好的倒數相乘再位移，沒有除法。
- **配置**：每一級一個 cursor，在一段空區段（連續的空格子）裡 bump：一次加法和比較。沒有 nursery 的 heap（和一定配在 old、沒有 site 要數的物件）走 inline 的快路（cppgc 的 `ObjectAllocator::AllocateObject`）：bump、寫 header，有 drop glue 的物件經過 mark table 設那一頁的 bit、在 cursor 上記一筆（換頁、sweep 交出頁、verifier 之前加回頁上的計數）；不看 `Site`。區段用完、large object、nursery、要數 site 的走 cold 的慢路（`HeapStats::slow_allocations` 數它）。配置的量在 cursor 拿到一段時照整段算（cppgc 的 `StatsCollector` 照 LAB 算）：`used_bytes` 扣掉 cursor 還沒用的尾巴，是精確的；`counted_bytes` 不扣，一次讀完，給每次操作後看長了多少的人（例如報給 JS engine 之前）；GC 的門檻先看整段算的、到了才扣尾巴確認。區段用完時拿同一頁的下一段，再來是那一級空格子最少的頁（mimalloc 的挑法：讓接近空的頁有機會空出來），再來是 pool 的空頁、discard 過的頁，最後是新的頁。large object 拿第一段夠長的連續空頁，沒有就接在最後面。物件寫完才寫 header、設 bit。
- **GC**：`Heap::mutate` 開始時，上一次 full GC 之後在 old 配置和升上去的量到了門檻（上一次留下的量，和 `min_allocation_bytes` 取大的，預設 2 MiB：heap 長到上次留下的 2 倍。cppgc 的 `HeapGrowing` 是 1.5 倍、最少多 640 KiB，但它的標記大多 concurrent、每次配置都算；這裡的 full GC 停住整個世界，年輕就死的不算，1.5 倍時 kun 的 gc-tree 這種全部活著的工作 full GC 太多，640 KiB 時存活率低的工作還是常做 full GC，V8 一次都沒有。V8 的 JS heap 照 GC 和 mutator 的速度長 1.1 到 4 倍）時做 full GC（platform 有背景的 worker 時改成到一半就開始 concurrent marking，下面），不然 nursery 滿了時做 scavenge；`stress` 打開時每個安全點輪流做兩種。full GC 先做一次把活的全部升到 old 的 scavenge（nursery 變空，slot set 也全空），再 mark-sweep old。Mark 從 root 表出發，照型別的 layout 只讀 `Member` 欄位（`HeapVector` 的陣列讀每條邊）。Marking 交給 heap 的 platform：root 先給呼叫的 thread，它的本地清單滿了一段（512 項，cppgc 的 marking worklist 的大小）才發布到全域，每發布一段叫醒一個 worker，platform 照可以拿的段數讓 worker 加入（V8 的 `GetMaxConcurrency`；開工時沒有段可以拿就不叫醒），所以小的或窄的圖都在 heap 的 thread 上標完：一段 64 項時，一串小樹（kun 的 `gc_bench` 的 tree）被切給 worker 標，拿的成本比標的多，比只用一個 thread 慢 5 倍；mark bit 先讀、沒標過才 atomic 地設上。所有的 thread 都沒有東西、全域也空了才結束；一個 worker panic 時，呼叫的 thread 不再等它，panic 在 `Heap::collect` 那裡繼續。Sweep 只讀 bitmap：一次 64 格找出空區段，有 finalizer 的死物件才讀它（跑 finalizer），沒有的完全不碰；heap 都整理好之後才跑 finalizer。`Heap::collect` 和沒有 worker 的 platform 在停頓裡 sweep 完（cppgc 的強制 GC 也是）；其他的照下面的「Concurrent sweep」。debug build 再把死掉的物件填上 `0xdb`，留著的錯的指標讀到的是毒值。
- **Concurrent marking**（V8 的 `ConcurrentMarking`，barrier 是 SATB 而不是它的 Dijkstra）：platform 有背景的 worker（`posts_jobs`）時，old 的量到了 full GC 門檻的一半（cppgc 開始 incremental marking 的範圍的下限），那個安全點開始 marking：一次把活的全部升到 old 的 scavenge（nursery 變空，快照只有 old），每個 root 當場標上，把 marker 交給 `post_job`，在 worker 上和 mutator 同時標。進行中：
  - **barrier**（snapshot at the beginning）：寫邊之前讀出舊值，是 old、還沒標的就標上、推進 mutator 本地的一段（滿了發布、叫醒 worker，安全點時發布手上的）；young 的和 0 不管。刪掉的 root 記在 root 表上，安全點時同樣標上推進去（root 在開始時全標了、之後加的 root 拿的是快照裡的或新配置的，TLA+ 的模型裡拿掉它也不漏標）。配置時的 init 不經過：格子原本是垃圾。
  - **black allocation**（V8 的 black area）：每一級的 cursor 和 scavenge 的 copier 每拿一段空區段，就把整段的 mark bit 用整個 word 的 or 設上，段裡的配置不再做事，快路徑不變；開始時現在的每段也標上；收尾時（和 copier 把段還回頁上時）清掉沒用完的。large object 配置時設 `marked`。所以 marking 期間新配置的和 scavenge 升上來的都是黑的。
  - **marker 跳過 young**：marking 只走 old。young 物件指到的 old 物件，不是開始時的快照裡的（被 SATB 保住），就是之後配置或升上來的（黑的）。
  - **發布**：marking 期間新配置的物件，mutator 寫完、mark bit 設好之後才用 release 寫進邊；背景的 marker relaxed 讀一批邊（16 條）之後一次 acquire 的 fence，看到邊就看得到它是黑的、不去掃（每條邊都 acquire 讀時，標一條鏈慢三分之一）。
  - **scavenge**：nursery 滿了時，heap 先 `cancel` marker 的 job（marker 在物件的邊界看 `should_yield`，把手上的發布出去、返回，`cancel` 等它們都返回），scavenge 照舊用全部的 worker，做完再 `post_job`：worklist 裡只有 old 的物件，不用更新。
  - **收尾**：marker 做完（全域沒有段、沒有 marker 在跑）之後的下一個安全點，或 old 撞到門檻時，在停頓裡收。marking 期間的門檻多一段 margin（V8 的 `old_generation_overshoot_margin`）：門檻的一半和 `HeapOptions::min_overshoot_bytes`（預設 32 MiB，V8 的 `kMinOvershoot`）取大的，不超過 cage 在門檻之外剩下的一半；marking 開始時（開始前的 scavenge 之後）算好，到收尾都不變，照 V8（`(max − limit)/2`）：跟著 old 長大重算的話，margin 每長一點就縮一點，實際只到剩下的約 1/3；沒有它時全部活著的工作 worker 常還沒標完就撞到門檻，剩下的在停頓裡標（graph-high 的收尾 p99 5.3 ms，有它時 2 µs），heap 多長的不到 1 MiB。收尾時：取消 job、發布 barrier 的本地段，剩下的用 `run` 平行做完（全部的 worker 加上 heap 的 thread，同一個 worklist），清掉黑的區段沒用完的 bit，關掉 barrier，然後把 sweep 交給背景（下面的「Concurrent sweep」）。`used` 和下一輪的門檻等 sweep 做完才定：sweep 找到的活的 bytes（套用每頁的結果時加總，加上標過的 large object），加上那之後配置的；在那之前 `used` 是 GC 前的量（含還沒掃的垃圾）加上之後配置的，門檻是上一輪的。V8 和 cppgc 在 marking 結束時用 marker 數的 bytes 設門檻；在這裡每個物件數一次讓標記慢了 3% 到 21%（graph-high 低於 cppgc），sweep 通常幾 ms 內就做完。`Heap::collect` 也先這樣收掉進行中的 marking，再做一次完整的 full GC（停頓裡從頭標：要它收掉 marking 期間死掉的）。heap drop 時先取消 job。
  - trace 裡開始是 `Gc.Pause` 裡的 scavenge 和 `Gc.MarkStart`，收尾的 `Gc.Pause` 裡的 `Gc.Mark` 是標記的收尾。`stress` 在有背景的 worker 時輪流做 scavenge、開始 marking、marking 中的 scavenge、收尾。
- **wasm engine 的 frame**（`Heap::enter_frames`）：wasm 的碼呼叫 embedder（DOM 的 host function，每個各自是一次操作）時，wasm 的 frame 還在 stack 上、拿著物件的 bits，heap 看不到。所以在 frame 裡，安全點不開始要讀 root 的 GC：不 scavenge（nursery 滿了改配置到 old）、不做 full GC、不開始也不收尾 marking（old 可以超過門檻）；sweep 照跑，marking 期間照樣發布 barrier 的段。這些 GC 由 engine 在拿得到全部 root 的地方做：wasm 配置時（`raw::alloc_bits` 回 `GcDue`）或 `Store::gc`，它從 stack map 收齊 root、交給 `Heap::safepoint_with_roots`。root 的 bits 先讀出來，scavenge 把它們接在 root 表的格子後面一起搬、做完寫回，marking 開始時一起標，verifier 一起走。收尾也只在交出 root 的地方，但不從它們標：SATB 下 frame 在開始之後拿到的，是快照裡的、新配置的或 young 的，和之後加的 `Persistent` 一樣；frame 的格子被覆寫不經過 barrier，等於刪掉一個開始時就標了的 root。檢查放在安全點的慢路徑（有工作時才走到），`mutate` 的快路徑不變。V8 在任何配置的地方都能 GC：JS 和 wasm 的 frame 用 safepoint table 找 root，Blink 的 C++ stack 用 conservative 的掃描（cppgc 由 `EmbedderStackState` 知道 stack 上有沒有指標）；這裡不掃 stack，代價是 wasm 呼叫 DOM 時配置的物件直接進 old。
- **Weak**（cppgc 的 `WeakMember`、`WeakPersistent`）：型別的 layout 另外列出 weak 的 offset，marker 和 scavenge 不從它往下走。weak root 在自己一張表裡（像 cppgc 的 weak persistent region），走 root 的地方都看不到它。
  - **full GC**：marker 掃一個物件時，讀它的 weak 欄位，目標是 old、還沒標的，把格子記下（每個 thread 各記、結束時合起來；目標已經標過的不記，像 cppgc 的 `RegisterWeakReferenceIfNeeded`）。收尾時這些格子的目標還沒標的清成 0，weak root 整張看一遍。marking 期間配置和升上來的黑物件不用記：SATB 下 mutator 拿得到的物件（快照裡的、新配置的、weak 讀出的）收尾時都標過，所以 marking 期間寫進任何欄位的值收尾時都標過，而開始前 nursery 已經清空，黑的物件的 weak 欄位都是 marking 期間寫的。
  - **scavenge**：weak 的邊不當 root。copy 完之後處理 copy 的 weak 欄位（掃 copy 時記下）、old 指向 young 的 weak 邊（寫 `WeakMember` 和配置時的 init 的 barrier 記進另一張 weak 的 slot set）和 weak root：目標搬走的改成新的位置（還是 young 的留在 weak 的 slot set），沒搬的（死了）清成 0。所以只被 weak 指著的年輕物件第一次 scavenge 就收掉（V8 的 scavenger 把 weak 當 strong，只有 JS 的 `WeakRef` 例外；DOM 的 weak 容器是常態）。
  - **讀取的 barrier**：marking 期間 `get` 讀到 old、還沒標過的物件，用 SATB 的同一段標上、推給 marker（快照可能已經到不了它，它現在是 mutator 的）。寫 weak 欄位不用 SATB 的 barrier（weak 的邊不留住東西），marking 期間照樣 release 寫。
- **Ephemeron**（cppgc 的 `EphemeronPair`）：型別的 layout 另外列出 pair 的 offset（key，value 在它後面 4 bytes）。
  - **full GC**：marker 掃到 pair 時，key 是 old 而標過、或是 young（old 的 marking 不判斷 young），就把 value 當 strong 標上；不然把 pair 記進 discovered 的清單（cppgc 的 `ProcessEphemeron`）。背景的 run 沒有段可拿時再看一次 discovered：key 已經標過的標它的 value、推進 worklist，反覆到沒有新的；收尾時也一樣，有新標的 value 就再 `run` 一次（cppgc 的 `ProcessWorklistsWithDeadline` 的迴圈）。最後 discovered 裡剩下的 key 都沒標，key 和 value 一起清成 0（cppgc 的 `ClearKeyAndValueIfKeyIsDead`）。marking 期間配置和升上來的物件的 pair 不用處理（同 weak 的論證）。寫 key 不用 SATB（同 weak），寫 value 用（同 strong 的邊）；讀 value 時先讀 key、經過 weak 讀取的 barrier（讀出的 value 活得和 key 一樣久）。
  - **scavenge**：照 V8 的 scavenger：value 一律當 strong 的邊，key 是 weak 的。copy 完之後，copy 的 pair 和 old 物件指向 young 的 key（寫 key 的 barrier 記進另一張 ephemeron 的 slot set，和 weak 的分開：清 key 時要一起清 value），key 搬走的改位置，死了的 key 和 value 一起清成 0。所以 key 死掉的年輕 value 多活一次 scavenge。
- **id 表**（`crates/elise/src/ids.rs`）：heap 外的程式（DOM 的 style、layout、paint）用 id 指物件。每個 heap 一張表，照 id 直接索引：一個目錄，每格指向一塊 1024 格（或空的），每格是物件的 offset（0 是沒有或死了）；id 從 1 一直往上數、不重複。查詢比對物件 header 的型別（`Erased` 不比），marking 期間經過 weak 讀取的 barrier。
  - **full GC**：收尾時整張走一遍（V8 的 weak global handle 也是），指向 old、沒標的清成 0，整塊清空的放掉：成批建立的物件 id 連在一起，成批死掉時整塊收回。
  - **scavenge**：`new_id` 時物件是 young 的，id 進一份清單（V8 的 global handle 的 `young_nodes_`）；copy 完之後只走清單，搬走的改位置、升上去的拿出清單、死了的清成 0。
  - Blink 的 `DOMNodeIds` 是一個 id → `WeakMember<Node>` 的 hash map，只給需要的節點發 id、`int` 數到頭會重用；這裡每個節點都有 id（style、layout、paint 在 heap 外用它），id 不重複，所以用陣列。
- **Concurrent sweep**（cppgc 的 concurrent sweeper，`crates/elise/src/heap/sweep.rs`）：concurrent marking 收尾（和 at-limit 的 full GC）的停頓裡，size class 的頁都清掉空區段、照 size class 列成清單交給 platform 的 posted job（最多一個 worker，cppgc 的 concurrent sweeper 也是：一頁約 0.3 µs，比叫醒一個 worker 還快，多個 worker 只是搶清單的鎖），死掉的 large object 當場放掉。job 經過 `MarkTable` 只讀 mark bit，算出每頁的空區段和活的數目，放進有鎖的清單；heap 的 thread 在安全點（`mutate`、`scavenge` 開始時）和配置的慢路徑把結果套到頁上（放進 `available`，照空格子由多到少，整頁空的進 pool，套用時 verifier 檢查那一頁），所以 `Space` 和配置的快路徑都和沒有 sweep 時一樣。某一級沒有掃好的頁可以配置時，heap 的 thread 從那一級還沒掃的清單拿一頁自己掃（V8 的配置一次掃一頁，cppgc 的 `SweepForAllocationIfRunning`）。V8 的 sweeper 直接寫頁的 free list，它的頁有好幾個 thread 在配置，這裡沒有。scavenge 照常做：升上去的物件只拿掃好的頁、pool 或新頁；還沒掃的頁上的死物件沒有 slot set 的記錄（收尾時有記錄的 old 物件都標過，`soundness.md`），所以不用過濾 slot set。finalizable 的 bitmap 和 mark bit 一起在 `Marks` 裡（atomic 的 word），每頁數 finalizable 物件和其中 heap 的 thread 那種的。有 heap 的 thread 那種物件的頁和那種死掉的 large object 不交給 job，heap 的 thread 在收尾之後的第一個安全點掃、跑 finalizer（頁上 `Send` 的也一起）；只有 `Send` 的 finalizable 物件的頁和那種死掉的 large object 交給 job（另一張清單，heap 的 thread 配置時不拿：不在操作中途跑 `Drop`），它先清掉死物件的 bit、跑 `Drop`、寫毒值，再算空區段（large object 的頁在套用時放掉）。`Drop` panic 時，那一頁回到清單、之後重掃（bit 已經清掉，不會 finalize 兩次，剩下的 leak），panic 在 heap 的 thread 下一次等 job 時往上拋。下一輪 marking 開始和 full GC 的停頓先取消 job、用 `run` 掃完剩下的、全部套用（V8 的 `EnsureMajorCompleted`、cppgc 的 `FinishIfRunning`）；heap drop 時先取消 job。heap 的 thread 在停頓外的 sweep 用計數記（`HeapStats::sweep_on_main_ns`、`pages_swept_on_main`），不發 trace 事件（cppgc 的 `kSweepOnAllocation` 也是）：一次只有約 0.3 µs。
- **Pool**：sweep 後整頁空的頁、死掉的 large object 的頁進 pool，任何一級和 large object 都能拿；在 pool 裡過了一整輪 GC 還沒人拿的，discard：記憶體還給作業系統、位址保留（macOS、Linux 用 `MAP_FIXED` 重新映射成沒有權限的記憶體，Windows 用 `MEM_DECOMMIT`）。platform 有 worker 時由 worker 做（`crates/elise/src/heap/discard.rs`，一個 posted 的 job、一個 worker）：系統呼叫的時間跟著還的 bytes（Apple M4 上 350 MiB 約 6 ms，連續的頁合成一次呼叫也一樣），放在收尾的停頓裡太長。sweep 把頁標成 `Discarding` 交給它，那時沒有人拿；還完之後的下一個安全點才列進 discard 過的頁，committed 也在那時才減。V8 讓頁在 pool 裡待 8 到 16 秒才由 worker 上延後的 task 還（`MemoryPool`），cppgc 平常不還。
- **碎片的量測**（V8 的 `--trace-fragmentation`，`crates/elise/src/heap/fragmentation.rs`）：`HeapOptions::measure_fragmentation` 打開時，每次 sweep 做完（一輪裡最碎的時候）和每次 marking 開始時（開始前的 scavenge 之後：V8 在這時挑要搬空的頁，之後的配置已經填掉一些空格子）走一遍頁，記在 `HeapStats::fragmentation` 和 `fragmentation_at_marking`：old 的 committed（nursery 的頁以外，pool 的算在內）、有物件的 size class 頁的格子的 bytes 和其中空的（頁上還沒交出去的空區段，加上 cursor 正在 bump 的那段的剩下），和照 V8 一般的 full GC 挑要搬空的頁的做法（`CollectEvacuationCandidates`，還沒量到 compaction 的速度時）：空的至少 70% 的頁、活的最少的先拿、搬的 bytes 最多 4 MiB，同一級的物件擠到最少的頁上之後能放掉的頁數，放不掉任何頁就一頁都不拿。只是量：沒有搬動物件的 compaction（kun 的 `gc_bench` 的 DOM 的工作、配置模式和重播上，marking 開始時照這個挑法幾乎放不掉頁：sweep 之後的配置先填最滿的頁的空格子，到下一次 marking 時空格子大多填回了）。kun 的 `gc_bench` 打開它（走一遍頁是幾 µs）。`HeapStats::old_ranges`、`old_range_slots` 數配置在 old 拿的空區段（配置的慢路徑，heap 的 thread 和 scavenge 的 thread 的）和它們的格子數：一段只有幾格就是碎的頁讓配置常走慢路徑。
- **Heap verifier**（V8 的 `--verify-heap`、cppgc 的 `MarkingVerifier`）：`HeapOptions::verify` 或 `stress` 打開時，每次 GC 之後從 root 自己重走一遍（不共用 marker 和 scavenger 的程式）。full GC 之後檢查 nursery 是空的、走到的物件都是完整的、標過的，沒走到的都沒標，頁的帳（空格數、空區段、`available`、pool、commit 和 `used_bytes` 的總數）都對；concurrent marking 收尾之後 nursery 可以有物件（走過去、不要求標），標過但走不到的只能是開始時 root 走得到的（開始時記下）、weak 讀取標上的物件當時走得到的（讀取時記下）或 marking 期間在 old 配置的（`publish` 時記下），也就是 SATB 的 floating garbage；每條 weak 的邊和 weak root 是 0 或指向標過的物件（concurrent 時也可以是 young 的）；走訪照 ephemeron 的語意（key 走到了才走 value，反覆到沒有新的），每個 pair 是兩個 0，或 key 和 value 都標過；id 表的每格是 0、標過的物件或（concurrent 時）young 的，沒有整塊都是 0 的塊；三種 slot set 記的格子都在活的物件裡（sweep 不看它們，所以不能有記錄落在釋放的格子上）；scavenge 之後檢查走到的 young 物件都在 nursery 現在的頁上、不是 `FORWARDED`（從頁的開頭一個一個走找到它），每條 old 指向 young 的邊都在 slot set 上（weak 的在 weak 的 slot set 上），weak 的邊和 weak root 指向 nursery 裡沒搬走的物件或 old 的物件，pair 的 value 當 strong 的邊走、key 照 weak 查（old 指向 young 的 key 在 ephemeron 的 slot set 上），key 是 0 時 value 也是 0，id 表指向 young 的格子都在 young 的清單上、清單上的都指向 young，nursery 的頁和用量對得上；不對就 panic，寫出物件、邊和頁。測試和 fuzz 都打開它；Miri 底下不開（`stress` 也不帶它）：Miri 找的是未定義行為，每次 GC 再走一遍整個 heap 讓它跑上半小時，verifier 的檢查由 `cargo test` 跑。
- **證明過的程式**：頁的 bitmap 搜尋（`next_bit`、`free_ranges`，`crates/elise/src/bits.rs`）寫在 Verus 的 `verus!` 裡，對任何長度的 bitmap 證明它找到的剛好是所有最長的連續的 0。一般的 build 拿掉規格和證明、編同一份程式；`elise` 因此依賴 `vstd`，版本和 Verus 執行檔一起釘。
- **和 JS engine 一起標記**（`crates/elise/src/js.rs`，Chrome 的 unified heap 裡 cppgc 的位置，照 cppgc 的物件的方式）：`HeapOptions::driven` 的 heap 不自己開始或收尾 old 的 marking、也不自己做 full GC（`collect` panic），由 engine 在它的 major GC 裡推進（kun 的 V8 那一側在它的 `bindings` 的 `unified_heap`，這裡的測試用自己的 engine）：`start_marking`（像 `Heap::mutate` 開始一次 concurrent marking：先做把活的全部升上去的 scavenge、標 root），engine 每一步 `advance_marking`（發布 barrier 的段，heap 的 thread 標它照排程落後的量，叫醒 worker；`atomic` 時在這裡做完），兩邊都做完才 `finish_marking`（沒做完就 panic）。`finish_marking` 回傳 heap 之後用了多少：driven 的 marking 數存活的 bytes（marker 走訪的物件的 slot，加上 marking 期間黑色進 old 的：配置的、scavenge 升級的），結束時 `used` 就是它（之後的 sweep 算出一樣的數字），engine 照它定下一次的門檻，如 V8 用 cppgc 標到的 bytes；不是 driven 的 heap 不數，照舊在 sweep 做完時才知道。排程（`crates/elise/src/heap/schedule.rs`）照 V8 和 cppgc 的 `IncrementalMarkingSchedule`：預計 500 ms 標完，照經過的時間算出現在該標到多少，扣掉已經標的（worker 每標 512 個就算進去，不等 run 結束），差多少在這一步補多少，上一步之後沒有進展時至少 64 KiB 的量，都不超過 engine 給這一步的時間；單位是物件數（marker 不數 bytes），用上一次 GC 的平均大小換算。trace 裡 engine 的步驟裡是 `Gc.Step`、停頓裡的推進是 `Gc.Mark`（在 engine 自己的 GC 的事件裡面，像 V8 的 `MC_INCREMENTAL_EMBEDDER_TRACING`、`MC_MARK_EMBEDDER_TRACING` 裡的 cppgc）。scavenge 照舊自己在安全點做。協定在 TLA+ 的模型上窮舉過（`soundness.md`）：
  - **不搬的物件**：driven 的 heap 裡，帶 `JsEdge` 的型別一律配置在 old（old 不 compact），所以 engine 記著的位址一直有效（cppgc 的物件不搬，Chrome 的 DOM 物件也沒有新生代）；不是 driven 的 heap 照常放 nursery。DOM 掛在這些物件上的資料用 `alloc_beside` 跟著放 old。剩下的短命物件不多時，heap 可以乾脆不用 nursery（`nursery_bytes: 0`，kun 的 JS 文件的 heap 就是）：scavenge 它們不比留給 old 的 GC 便宜。
  - **wrapper**：存物件的位址（`Mutation::engine_address`）；engine 標到 wrapper 時從它的 thread 交過來（`WrapperLocal::hand`：當場標上、推進 marker 的 worklist）。scavenge 和 old 的 marking 都不從 wrapper 開始：wrapper 指著的都是 old 的，scavenge 不管它們；marking 期間新 wrap 的物件是黑的配置或快照裡的。讀回（`Mutation::from_engine`）時有讀取的 barrier：SATB 的快照不含只被 wrapper 留著的物件，engine 的 Dijkstra barrier 也不管 script 丟掉 wrapper。
  - **JS 的邊**（`JsEdge`）：型別的 layout 另外列出它的 offset，marker 掃到物件時不讀它，把位址交給 `JsEdgeSink` 的 local（每個 run 和 heap 的 thread 的每一步第一次用到時建，結束時 drop）。
- **heap snapshot 的走訪**（`Heap::walk`，`crates/elise/src/heap/walk.rs`）：走的是配置留下的，不是 root 走得到的（engine 的 wrapper 拿著的物件從 heap 裡哪裡都走不到）。sweep 收完的安全點上，size class 的頁上的格子除了頁上的空區段和那一級的 cursor 正在 bump 的那段，每格都是物件；large object 的頁是它；nursery 的頁從頭到頂是物件和 filler。header 沒有登記的型別的格子（新的頁的 0、debug build 的 poison）跳過。欄位的名字由 derive 寫進型別的 layout（`FieldInfo::name`，C 字串：V8 的 heap profiler 在 callback 之後才讀邊的名字）；執行時的型別的邊照它的 layout 走，沒有名字，`I31` 跳過。
- **Heap 的 drop**：每個還在的、有 drop glue 的物件（old 的和 nursery 的清單上的）的 finalizer 跑一次。**root 不能活得比 heap 久**（Blink 的 `PersistentRegion` 一樣）：`Persistent` 只記表的位址、不計數。拿著 root 和 heap 的 struct 把 heap 放在最後一個欄位（欄位照宣告的順序 drop）。違反時 heap 留下它的 root 表（不是 UB），debug build 接著 panic。
